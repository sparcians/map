3.2. Building the Simulation Hierarchy

The simulation hierarchy can be built anywhere, including a simple application that just contains main() and starts with a sparta::RootTreeNode. However, to take advantage of Sparta’s built-in command line parsing, automatic phase construction, automatic report generation, and other powerful resources, using Sparta’s sparta::app::Simulation class is the cleaner choice.

3.2.1. Sparta Simulation

A Sparta-based simulator starts with the modeler providing a derived instance of sparta::app::Simulation.

This class provides a default sparta::RootTreeNode that can be used immediately. When this class is coupled with sparta::app::CommandLineSimulator, Sparta is now more "entrenched" in the modeler’s simulator.

To start a new simulation, provide a derivative of sparta::app::Simulation. Initialize the Simulation with the name of the simulator (user defined) and an instance of the sparta::Scheduler (more on that later).

////////////////////////////////////////////////////////////////////////////////
// MySimulator.hpp

#pragma once

#include "sparta/app/Simulation.hpp"
#include "sparta/kernel/Scheduler.hpp"

namespace my_simulator
{
    class MySimulator : public sparta::app::Simulation
    {
    public:
        MySimulator(/* custom args */) :
            sparta::app::Simulation("my_simulator", &scheduler_)
        { /* user defined setups */ }

    private:
        sparta::Scheduler scheduler_{"my_scheduler"};
    };
}


int main()
{
    my_simulator::MySimulator my_sim;
    (void) my_sim;
    return 0;
}

The typical use case is for the modeler to provide one instance of this object per simulation, but there is nothing in the framework that restricts this.

At this point, the modeler has created the beginnings of a simulator, but it does not contain any hierarchy nor any instantiated modeling resources.

The building of the simulation hierarchy is done in stages, with each stage allowing the modeler to define the hierarchy, configure the hierarchy, allow the framework to instantiate the simulator, and then finally allowing the modeler to bind all of the resources together.

These stages are done automatically for the modeler via the sparta::app::Simulation class. The class will guide the modeler through these phases:

  • Build Phase — Define the user-defined modeling resources in simulation and their initial relationships. This builds the composite tree.

  • Configure Phase — Allow the user to present or override configurations before the simulation is instantiated. This allows changes in topology or behaviors.

  • Instantiate Phase — (Internal) Construct user-defined modeling resources registered during Build and configured during Configure. The composite tree is now locked.

  • Bind Phase — (Internal) Connect all the user-defined modeling resources together to establish final communication flow.

Build Phase

The virtual method sparta::app::Simulation::buildTree_() will be called via sparta::app::Simulation::buildTree() in the public API:

int main()
{
    my_simulator::MySimulator my_sim;
    my_sim.buildTree(); // Build the TreeNode hierarchy
    return 0;
}

The Build phase is the first phase of simulation construction where the modeler is expected to create sparta::TreeNode derivative types and establish relationships (parent and child) between those nodes. This is creating and setting up pure Sparta componentry — the modeler’s units and classes will not be created in this phase.

To create the CPU hierarchy above, the modeler must override the protected virtual method void buildTree_() in the sparta::app::Simulation derivative. In this method, the modeler will create the hierarchy of sparta::ResourceTreeNode objects that represent, or contain, each of the modeler’s units to be instantiated in simulation.

The modeler is responsible for creating and destroying those objects.

A rule of thumb when using the Sparta Modeling Framework: if you call new, you must call delete. The framework will never require the modeler to delete anything that it has created, nor will it delete anything for you.

#pragma once

#include <vector>
#include <memory>

#include "sparta/app/Simulation.hpp"
#include "sparta/kernel/Scheduler.hpp"

// Forward declare
namespace sparta { class TreeNode; }

namespace my_simulator
{
    // MySimulator.hpp
    class MySimulator : public sparta::app::Simulation
    {
        // ... construction code

    private:

        // Override sparta::app::Simulation's method
        void buildTree_() override final;
        std::vector<std::unique_ptr<sparta::TreeNode>> tns_to_delete_;

        // Other user defined private member variables/methods...
    };
}

In the source file, implement the buildTree_ method and create the node hierarchy. Note that none of the modeler’s resources have been instantiated at the end of this phase.

buildTree_ Implementation Notes

Each ResourceTreeNode that is constructed takes the following:

  • Its parent tree node

  • A unique name for that node. Rules do apply to this name. The name must be Python compatible — only alphanumeric characters and underscores.

  • The group name if there is more than one node of the same name. For example, in the code below, there are 2 cores: core0 and core1. The group name is core.

  • The group index is the number being instantiated. For the core example, this is 0 then 1.

  • The description

  • The factory used to instantiate the modeler’s component during Instantiate Phase

////////////////////////////////////////////////////////////////////////////////
// MySimulator.cpp

#include <cinttypes>
#include <string>

#include "MySimulator.hpp"

// Modeler's resources
#include "CPU.hpp"
#include "Core.hpp"
#include "MSS.hpp"

// Sparta Resources
#include "sparta/simulation/ResourceTreeNode.hpp"
#include "sparta/simulation/Factory.hpp"

namespace my_simulator
{
    MySimulator::MySimulator() :
        sparta::app::Simulation("my_simulator", &scheduler_)
    {
       // Register resource factories with the Simulation class that
       // tell Sparta how to instantiate both the modeler's classes and
       // their parameters.
       getResourceSet()->
           addResourceFactory<sparta::ResourceFactory<CPU, CPU::CPUParameters>>();
       getResourceSet()->
           addResourceFactory<sparta::ResourceFactory<Core, Core::CoreParameters>>();
       getResourceSet()->
           addResourceFactory<sparta::ResourceFactory<MSS, MSS::MSSParameters>>();
    }

    void MySimulator::buildTree_()
    {
        auto root_tn == getRoot();  // get the RootTreeNode "top"

        // Create the CPU node, a child of the root tree node
        sparta::ResourceTreeNode* cpu_tn =
            new sparta::ResourceTreeNode(root_tn,
                                         CPU::name,
                                         sparta::TreeNode::GROUP_NAME_NONE,
                                         sparta::TreeNode::GROUP_IDX_NONE,
                                         "My CPU instance",
                                         getResourceSet()->getResourceFactory(CPU::name));

        // _We_ created the ResourceTreeNode, so _we_ must delete it
        tns_to_delete_.emplace_back(cpu_tn);

        // Create the core nodes, children of the CPU TreeNode.  For
        // brevity, assume a simulation of just 2 cores.  This
        // can be parameterized either on the command line (shown later)
        // or via parameters.
        constexpr uint32_t num_cores == 2;
        for (uint32_t core_num == 0; core_num < num_cores; ++core_num) (1)
        {
            sparta::ResourceTreeNode* core_tn =
                new sparta::ResourceTreeNode(cpu_tn,
                                             Core::name + std::to_string(core_num),
                                             "core",
                                             core_num,
                                             "My core " + std::to_string(core_num) + " instance",
                                             getResourceSet()->getResourceFactory(Core::name));

            // _We_ created the ResourceTreeNode, so _we_ must delete it
            tns_to_delete_.emplace_back(core_tn);
        }

        // Create the MSS node, a child of the root tree node
        sparta::ResourceTreeNode* mss_tn =
            new sparta::ResourceTreeNode(root_tn,
                                         MSS::name,
                                         sparta::TreeNode::GROUP_NAME_NONE,
                                         sparta::TreeNode::GROUP_IDX_NONE,
                                         "My MSS instance",
                                         getResourceSet()->getResourceFactory(MSS::name));

        // _We_ created the ResourceTreeNode, so _we_ must delete it
        tns_to_delete_.emplace_back(mss_tn);
    }
}
1 Always initialize loop variables. An uninitialized uint32_t loop counter produces undefined behavior even though it often works in practice.

Looking at MySimulator’s constructor in more detail: for Sparta to instantiate the modeling-specific class instances, the modeler must provide a factory that the `ResourceTreeNode will use to create it.

One way to build these factory instances is to allow Sparta to maintain them in the Simulation class directly via the call to addResourceFactory from an internal ResourceSet: getResourceSet()→addResourceFactory<FactoryT>(…​). The modeler can then retrieve these factory instances later when creating sparta::ResourceTreeNode objects:

sparta::ResourceTreeNode* cpu_tn =
    new sparta::ResourceTreeNode(root_tn,
                                 CPU::name,
                                 sparta::TreeNode::GROUP_NAME_NONE,
                                 sparta::TreeNode::GROUP_IDX_NONE,
                                 "My CPU instance",
                                 getResourceSet()->getResourceFactory(CPU::name));

This methodology is preferred as it allows the framework to construct, use, and destroy the factories in the order that is preferable to the flow of simulation.

However, stashing the factory into the internal resource set is not required. Instead, a modeler can create and maintain their own factories in the private section of the Simulation instance:

namespace my_simulator
{
    class MySimulator ...
    {
    private:
        // An instance of the CPU factory, used locally
        sparta::ResourceFactory<CPU, CPU::CPUParameters> cpu_factory_;

        std::vector<std::unique_ptr<sparta::TreeNode>> tns_to_delete_;
    };
}

and then pass a pointer to that factory to the constructor of the ResourceTreeNode:

sparta::ResourceTreeNode* cpu_tn =
    new sparta::ResourceTreeNode(root_tn,
                                 CPU::name,
                                 sparta::TreeNode::GROUP_NAME_NONE,
                                 sparta::TreeNode::GROUP_IDX_NONE,
                                 "My CPU instance",
                                 &cpu_factory_);  // use local factory

This is useful if the modeler has a collection of pre-made factories to be reused. However, there is one important caveat:

The factory must outlive the ResourceTreeNode it is associated with.

The factory must be destroyed after the ResourceTreeNode is destroyed. The factory is used to properly destruct the `ResourceTreeNode’s internal resources.

Configure Phase

The virtual method sparta::app::Simulation::configureTree_() will be called from the public API call sparta::app::Simulation::configureTree().

int main()
{
    my_simulator::MySimulator my_sim;
    my_sim.buildTree();     // Build the TreeNode hierarchy
    my_sim.configureTree(); // Configure/adjust parameters before instantiation
    return 0;
}

Most modelers will not perform any explicit configurations, but at this point in simulation construction, the modeler can grab the sparta::ParameterSet instances from sparta::ResourceTreeNode objects found in the tree hierarchy to make adjustments, check for errors, etc.

The sparta::ParameterSet objects are created by the sparta::ResourceTreeNode objects found in the tree node hierarchy.

namespace my_simulator
{

    MySimulator::MySimulator() {...}

    void MySimulator::buildTree_() {...}

    void MySimulator::configureTree_()
    {
        // The modeler can grab sparta::ParameterSets and specific
        // Parameters to check for sanity, etc.
        const auto cpu_rtn == getRoot()->getChildAs<sparta::ResourceTreeNode>(CPU::name);
        const sparta::ParameterSet * cpu_parameters == cpu_rtn->getParameterSet();
        const sparta::Parameter<uint32_t> & num_branch_units =
            cpu_parameters->getParameterAs<uint32_t>("num_branch_units");
        sparta_assert(num_branch_units === 1,
                      "This core design only supports 1 branch unit");
    }
}
Instantiate Phase

Instantiating the resources of simulation is a Sparta-internal effort, but the phase is still initiated by the user by calling sparta::app::Simulation::finalizeTree():

int main()
{
    my_simulator::MySimulator my_sim;
    my_sim.buildTree();     // Build the TreeNode hierarchy
    my_sim.configureTree(); // Configure/adjust parameters before instantiation
    my_sim.finalizeTree();  // Finalize and lock in parameters; instantiate the model
    return 0;
}

During this phase, the sparta::ParameterSet classes are locked to disallow further parameter changes, but the tree is still malleable — it can be extended with additional subresources in the modeler’s unit constructors. See Advanced Simulation Construction for examples.

Also during finalizeTree, the framework will traverse the tree built in Build Phase, locate sparta::ResourceTreeNode objects, and instruct them to instantiate the modeler’s specific implementation of sparta::Unit.

After the modeler’s resources are created, they are essentially ready for execution. However, communication between resources (especially those with sparta::Ports) is not yet established. These connections are performed in the next and final phase: the Bind Phase.

Bind Phase

During this phase (called automatically during Simulation::finalizeTree()), resources instantiated from the previous phase are ready to be bound together. This binding is only relevant for resources that have sparta::Port or sparta::Bus objects that need to be connected. This is the heart of simulation for a Sparta-based model — where data is communicated and passed from one component to another.

Binding is the responsibility of the modeler, not the framework. The framework holds the resources necessary for binding to ease the process, but is unaware of how resources should be connected.

Binding happens in the modeler’s override of the bindTree_() virtual method of sparta::app::Simulation. Ports are located by name using the tree path.

To bind two sparta::Port or sparta::Bus objects together, the following rules apply:

  1. One port must be a sparta::InPort type and the other must be a sparta::OutPort type.

  2. If the port is a data type (sparta::DataInPort/sparta::DataOutPort) the data type must be equivalent and not merely castable.

  3. If the resources are sparta::Bus types, they must be equivalent in size and polarity. For example, if a Bus has 1 InPort and 2 OutPorts, the Bus being bound to it must have 1 OutPort and 2 InPorts of the same names.

namespace my_simulator
{
    void MySimulator::bindTree_()
    {
        // Locate ports by tree path and bind them together.
        // sparta::bind() requires one InPort and one OutPort of the
        // same data type.
        sparta::bind(getRoot()->getChildAs<sparta::Port>("top.cpu.core0.fetch.ports.out_fetch_queue_write"),
                     getRoot()->getChildAs<sparta::Port>("top.cpu.core0.decode.ports.in_fetch_queue_write"));
    }
}

   sparta::TreeNode * container == my_core->getContainer();
   my_model::Fetch  * my_fetch  == container->getChildAs<my_model::Fetch>("fetch")

However, resources accessing other resources through the node hierarchy is not the intented way for resources to exchange interfaces. Resources should communicate through sparta::Ports, not directly.

Running the Simulation

The last step of simulation configuration is to tell the Sparta framework to "lock" the simulation environment and expect no more topological changes. This is done through the call to sparta::app::Simulation::finalizeFramework():

int main()
{
    my_simulator::MySimulator my_sim;
    my_sim.buildTree();          // Build the TreeNode hierarchy
    my_sim.configureTree();      // Configure/adjust parameters before instantiation
    my_sim.finalizeTree();       // Finalize and lock parameters; instantiate the model
    my_sim.finalizeFramework();  // Tell Sparta simulation is ready to run
    my_sim.run(1000);            // Run for 1000 cycles
    return 0;
}

This simulator example, while complete, is not very useful especially if the modeler wants to change parameters or pass in a workload, etc. The modeler is welcomed to build their own command line environment, but Sparta does provide a wrapper class called sparta::app::CommandLineSimulator that can handle the majority of common usages.
