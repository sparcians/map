11.3. When to Use Precedence (and When Not To)

Establishing explicit precedence rules is not required in most Sparta models. The framework’s phase system and auto-precedence handle the vast majority of ordering needs automatically. Understanding when explicit precedence is and is not needed prevents both under-specification (ordering bugs) and over-specification (unnecessary complexity).

11.3.1. Precedence Is Not Needed: Non-Zero Cycle Ports

The most common modeling pattern — producers sending data over ports with a non-zero cycle delay — requires no explicit precedence declarations at all.

The ordering works automatically because:

  • Producers drive ports with a non-zero cycle delay, most likely in the Tick phase

  • Data is delivered to the receiving block on the PortUpdate phase in the next cycle

  • Each port callback schedules the UniqueEvent during the callback

  • The UniqueEvent callback fires on the Tick phase later in the same cycle — always after all PortUpdate callbacks have run

Since PortUpdate always precedes Tick, the framework guarantees the UniqueEvent fires after all port data has arrived. No registerConsumingEvent calls are required.

// Non-zero cycle ports -- no explicit precedence needed
sparta::DataInPort<InstPtr> in_inst_{&unit_port_set_, "in_inst", 1}; (1)
sparta::UniqueEvent<>       ev_process_{&unit_event_set_, "ev_process",
                                         CREATE_SPARTA_HANDLER(MyUnit, process_)};

MyUnit::MyUnit(sparta::TreeNode* node, const MyParameters* params) :
    sparta::Unit(node)
{
    in_inst_.registerConsumerHandler(
        CREATE_SPARTA_HANDLER_WITH_DATA(MyUnit, receiveInst_, InstPtr));
    // No registerConsumingEvent needed -- PortUpdate precedes Tick automatically
}

void MyUnit::receiveInst_(const InstPtr & inst) {
    pending_inst_ = inst;
    ev_process_.schedule();  // fires in Tick phase -- after all PortUpdate callbacks
}
1 The 1-cycle delay means data arrives in PortUpdate phase next cycle. ev_process_ fires in Tick phase of that same cycle, always after the callback.

11.3.2. Precedence Is Needed: 0-Cycle Ports

Explicit precedence is required when 0-cycle ports are involved. When the framework detects a 0-cycle port, the port delivery is promoted to the Tick phase — the same phase where the UniqueEvent runs. Without explicit ordering, the UniqueEvent may fire before all port callbacks have delivered their data.

The ordering problem:

  • The producer’s events fire in the Tick phase and drive 0-cycle ports

  • Data is delivered to the block in the same Tick phase

  • Each callback schedules the UniqueEvent — also in Tick

  • Without explicit ordering, the UniqueEvent may fire before all port callbacks have run in the same Tick phase

The solution is registerConsumingEvent and registerProducingEvent:

// 0-cycle ports -- explicit precedence required
sparta::DataInPort<InstPtr> in_inst_{&unit_port_set_, "in_inst", 0}; (1)
sparta::UniqueEvent<>       ev_process_{&unit_event_set_, "ev_process",
                                         CREATE_SPARTA_HANDLER(MyUnit, process_)};

MyUnit::MyUnit(sparta::TreeNode* node, const MyParameters* params) :
    sparta::Unit(node)
{
    in_inst_.registerConsumerHandler(
        CREATE_SPARTA_HANDLER_WITH_DATA(MyUnit, receiveInst_, InstPtr));

    // Required: tell the DAG that ev_process_ must fire AFTER
    // in_inst_ has delivered its callback
    in_inst_.registerConsumingEvent(ev_process_); (2)
}
1 The 0-cycle delay promotes delivery to Tick phase — same as ev_process_. Without explicit ordering the firing order is undefined within Tick.
2 registerConsumingEvent adds a DAG edge: port callback → ev_process_. The framework enforces this ordering automatically.

For the producer side, registerProducingEvent ensures the producer’s event fires before any downstream 0-cycle port consumers:

// In the producer unit
sparta::DataOutPort<InstPtr> out_inst_{&unit_port_set_, "out_inst"};
sparta::UniqueEvent<>        ev_produce_{&unit_event_set_, "ev_produce",
                                          CREATE_SPARTA_HANDLER(ProducerUnit, produce_)};

ProducerUnit::ProducerUnit(sparta::TreeNode* node, const ProducerParameters* params) :
    sparta::Unit(node)
{
    // Tell the DAG: ev_produce_ fires before any consumer of out_inst_
    out_inst_.registerProducingEvent(ev_produce_); (1)
}
1 The framework adds the ordering between ev_produce_ and all downstream consumers automatically at DAG finalization — no per-consumer registration required.

11.3.3. Decision Guide

Situation Precedence Needed? Reason

Non-zero cycle ports, UniqueEvent in Tick

No

PortUpdate always precedes Tick — framework handles ordering

0-cycle ports, UniqueEvent in Tick

Yes

Both port delivery and UniqueEvent are in Tick — ordering is undefined without explicit DAG edges

Multiple producers, non-zero cycle ports

No

All port callbacks fire in PortUpdate, UniqueEvent fires in Tick — phase separation is sufficient

Multiple producers, 0-cycle ports (mux pattern)

Yes

See Modeling a Mux: The Ordering Problem for the complete solution using registerConsumingEvent on each input port

Events ordering within the same phase

Yes

Use >> or EventGroup to establish intra-phase ordering (see [_intra_phase_ordering_with_the_dag])

11.3.4. Key Takeaways

The default case requires no explicit precedence. For the vast majority of pipeline models — non-zero cycle ports driving a UniqueEvent — the PortUpdate → Tick phase ordering is sufficient and no registerConsumingEvent calls are needed.

0-cycle ports are the exception. When a port has zero delay, delivery is promoted to Tick phase, breaking the automatic ordering guarantee. Always call registerConsumingEvent on every 0-cycle InPort and registerProducingEvent on every 0-cycle OutPort whose producer event must fire first.

Over-specifying precedence is harmless but unnecessary. Adding registerConsumingEvent to non-zero cycle ports does not break anything — the DAG edge is simply redundant. However, excess precedence declarations add noise to the DAG, slow finalization slightly, and make the code harder to read. Add only the edges the model actually requires.
