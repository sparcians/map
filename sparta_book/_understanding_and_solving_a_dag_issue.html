11.4. Understanding and Solving a DAG Issue

By default the Sparta Modeling Framework will order events based on an evaluated flow control between units. This is done through the auto-precedence mechanism in the Sparta Unit.

11.4.1. Auto-Precedence: How It Works

Auto-precedence can be disabled by calling setAutoPrecedence(false) in the derivative class of the sparta::Unit that exhibits the ordering issues. However, this may cause additional issues while not resolving the current one. See Potential Fixes for DAG Issues

After the binding phase of simulation is complete, the framework will comb through the simulation tree looking for bound OutPorts and follow them to bound InPorts. The framework assumes this is a Producer/Consumer relationship: the Producer contains the OutPort, the Consumer contains the InPort.

For the Consumer, the framework will automatically apply precedence rules between events in the Producer and Consumer if the InPort is constructed with a 0 cycle delay. This concept is covered in When to Use Precedence (and When Not To). Behind the scenes the framework is building a Directed Acyclic Graph or DAG to ensure there are no cyclic behaviors.

Using the DAG, the framework will automatically set the need for event ordering based on established uses of Ports and Events using the following rules:

  1. The modeler has communicated during construction the intended delay between an OutPort/InPort (0 cycle or not)

  2. The modeler has set up intended ordering of events using precedence (see Intra-Phase Ordering with the DAG)

  3. The modeler has registered producing/consuming events with ports

Before simulation finalization, the DAG is finalized. As the DAG finalizes the ordering of events registered (some are direct from the modeler, others from Ports), if the DAG determines a cyclic behavior, the DAG will stop finalization (will assert) and communicate the issue.

In most cases, the issue is clear. For example, take the Producer/Consumer with 2 ports between them:

Since the two Ports in simulation are both 0 cycles, the framework assumes that the produce_data_event will be scheuled in the same cycle the Consumer sends a signal on the out_data_received_port. If the modeler explicitly tells the framework this is the case, the framework will establish this expected ordering through the in_data_received_port:

    in_data_received_port.registerConsumingEvent(produce_data_event);

When the Consumer sends the signal on the out_data_received_port, the framework now knows that produce_data_event will be scheduled.

The framework still assumes that the produce_data_event might drive the Unit’s OutPorts, so the framework will establish an order between produce_data_event and the out_data_received_port, which in turn establishes an order between any events registered with any in ports connected to out_data_received_port. For this example, that event is consume_data_event in the Consumer.

If the Consumer registered that event as a producer to out_data_received_port, the cyclic behavior starts creeping in:

    out_data_received_port.registerProducingEvent(consume_data_event);
