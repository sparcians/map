3.1. Sparta Classes for Simulation

As an example of a simulation hierarchy, take a generic SoC design which consists of multiple cores and a memory subsystem (mss). Each core consists of subresources (fetch, decode, rename, etc). Each named object in the graph is considered a node or placeholder. The resource (if appropriate) will be instantiated later.

The top level node is, by default, named top and is the root of all resources in the example SoC. In Sparta, this is known as the sparta::RootTreeNode. Simulation typically contains one sparta::RootTreeNode, but nothing in the framework disallows multiple roots.

Note that in Sparta, a "root" tree node is always of type sparta::RootTreeNode called top if constructed without a name. This top node is created automatically when a sparta::app::Simulation object is instantiated (sparta::app::Simulation::getRoot()).

Each node of the hierarchy represents a sparta::TreeNode which is the main "node container." This container will hold everything related to that component like the component’s ParameterSet, PortSet, StatisticSet, and the modeler’s specific Unit.

The modeler is responsible for creating these nodes, establishing the relationships between them, and eventually destroying them. This relationship is built on top of the Composite Pattern from Design Patterns.

This hierarchy and component relationship is what will be represented in simulation and is at the heart of the Sparta Simulation Framework and the modeler’s simulator. Everything in simulation refers to these constructed artifacts and their relationships.

The modeler begins simulator development by creating a representation of the graph using sparta::TreeNode objects for placeholders and sparta::ResourceTreeNode for resources.

3.1.1. Sparta TreeNode

As mentioned above, Sparta requires a modeler to build a simulation hierarchy to represent those resources in simulation. Each of those nodes is, or a derivative of, a sparta::TreeNode.

Referring back to the Composite Pattern, sparta::TreeNode is-a Component, a Leaf, and a Composite. When the modeler creates the tree, that modeler is actually creating sparta::TreeNode instances to reside in the tree and then establishes parent-child relationships between them.

In practice, the modeler will most likely construct a sparta::ResourceTreeNode derived type. This class is a special type of sparta::TreeNode that allows Sparta to instantiate and maintain model-specific units and resources used in simulation.

3.1.2. Sparta ResourceTreeNode

The sparta::ResourceTreeNode is a derivative class of sparta::TreeNode and is aware of modeling resources that need to be instantiated including the modeler’s specific derivative of a sparta::Unit or sparta::Resource.

Specifically, the sparta::ResourceTreeNode is the main container for the following resources:

  1. sparta::Unit — The base class that the modeler will create their component from (Fetch, Decode, etc)

  2. sparta::ParameterSet — The parameters used by the modeler’s sparta::Unit to configure (FetchParameterSet, DecodeParameterSet, etc)

The sparta::ResourceTreeNode will instantiate the modeler’s unit as well as the parameters it uses. However, by itself, the sparta::ResourceTreeNode does not know how to instantiate the modeler’s modeling resources. To instantiate those resources, sparta::ResourceTreeNode requires the modeler to provide an instance of a sparta::ResourceFactory or a derivative of sparta::ResourceFactoryBase.

Factories are a common practice in software development, allowing a framework to remain type-agnostic, but giving an opportunity for the user to instantiate their own instance of a class.

For convenience, Sparta provides the generic derived factory sparta::ResourceFactory if the modeler has no special construction requirements. See the Factories section to learn how to create a custom factory to build specialized simulation tree structures.

During finalization of the framework (documented in the next section), the sparta::ResourceTreeNode will use the given factory to instantiate the user-defined modeling component.
